# Independent forensic audit: provider live-safety and paid submissions

Audit only. No production code, test or existing steering document was modified.
Scope is the uncommitted offline provider-readiness work sitting on top of
`5baebd2` ("Establish representation-invariant thumb-surface compilation").

Every finding below was **measured**, not read off the source. Where a claim in
the code or the previous slice report turned out to be stronger than the
mechanism behind it, the measurement is quoted.

**The audit itself made no network access, read no real credential, loaded no
`.env`, and created no provider job.** All probes ran with provider and proxy
variables cleared, with synthetic secrets, with fake transports, and under a
socket guard stricter than the project's own (loopback forbidden as well).

## 2. The real call graph

Every path that can produce outbound traffic ends at exactly one place:

```
transport.UrllibTransport.send()  ->  urllib.request.urlopen()
```

Nothing else in `tools/assetgen/` calls `urllib`, `http.client`, `socket` or
`requests`. There is no subprocess that performs provider traffic; the only
subprocess is the Godot binary spawned by `rig_ingest`, which does local asset
work. So the **lowest common network boundary is the injected transport**, and
every adapter reaches it through `send_with_retry` or a direct
`self.transport.send(...)`.

Above that boundary the guard structure is *not* uniform, which is the central
finding of this audit:

| Entry point | Barrier 1 `--live` | Barrier 2 opt-in | Barrier 3 plan digest | Ledger claim |
| --- | --- | --- | --- | --- |
| `autorig --submit` | yes | yes | **yes** | **yes** |
| `shield-multiview --submit` | yes | yes | **no** | **no** |
| `shield-3d --submit` | yes | yes | **no** | **no** |
| `auth-smoke --live` | yes | **no** | n/a | n/a |
| `poll` / `resume` / `download` / `cancel` | yes | yes | n/a by design | n/a |
| `JobOrchestrator(...)` constructed directly | yes | yes | **no** | **no** |
| `UthanaProvider(...).submit()` called directly | **no** | **no** | **no** | **no** |

Barriers 1 and 2 live in `JobOrchestrator._require_live`, which *is* at the
network boundary for everything routed through the orchestrator. Barrier 3 and
the at-most-once ledger claim live in `cli.authorize_paid_submission`, which
only `cmd_autorig` calls. The docstring on that function calls it "the single
chokepoint every paid command passes through"; measured, it is the chokepoint
for one of three paid commands.

Calling an adapter's `submit()` directly bypasses everything. That is expected
for a library seam and is **not** a defence against a hostile local process:
anything that can import the module can also read the environment directly. The
threat model these barriers actually address is accidental automation — a
copied flag, a leftover environment variable, an agent that wanted a command to
work. Against that they are effective. Against a hostile local process they are
not, and nothing in the design claims otherwise.

**A plan SHA-256 is neither a secret nor a signature.** It is a content digest
over a document that anything can recompute offline. It proves only that the
approver saw *this* configuration; it cannot prove *who* approved, and it can be
regenerated by any process that can read the input file. Its whole value is
freshness — it invalidates itself when the bound fields change.

## 3. Findings

Severity is about the declared contract and the money at risk, not about how
hard a bug is to reach.

### BLOCKER 1 — `auth-smoke --live` reaches the provider and reads the credential with barrier 2 absent

**Where:** `tools/assetgen/cli.py::cmd_auth_smoke`

**Reproduction (measured):** with `MESHY_API_KEY` set to a synthetic value,
`EOM_ALLOW_PAID_PROVIDER_CALLS` unset, and `UrllibTransport` replaced by a
counting transport:

```
case:    auth-smoke --live, synthetic creds, NO opt-in
outcome: OUTBOUND: GET https://api.meshy.ai/openapi/v1/balance
outbound_requests: 1
```

**Broken contract:** `docs/ASSET_PROVIDER_PIPELINE.md` and `live_gate.py` both
state that `--live` alone is not permission and that a run lacking the opt-in
fails closed *before* any credential is read. The slice requirement is explicit:
"Med `--live` men utan opt-in: fail-close före credentialläsning."

**Why it happens:** `cmd_auth_smoke` builds the orchestrator only to borrow its
`provider_factory`, then calls `provider.auth_smoke()` directly. It never routes
through `JobOrchestrator._require_live`, so barriers 1 and 2 are never evaluated
— the only gate is the command's own `if not args.live` check. Reaching
`auth_smoke()` calls `_headers()`, which materialises the key.

**Actual risk:** no paid task is created (the `balance` and `org` queries are
read-only), so the money risk is nil. The real damage is to the two properties
the slice exists to establish: a single flag again opens provider traffic, and a
credential is read on a run that the documented model says must already have
failed. It also proves a key works, which is exactly what the slice said it
would not do.

**Why the tests miss it:** every barrier regression drives `autorig` or the
orchestrator. No test invokes `auth-smoke`, and no test asserts that the set of
network-reaching CLI commands is exactly the set that passes through
`_require_live`.

**Minimum fix:** call `orchestrator._require_live("auth-smoke")` (or
`LiveAuthorization.authorize_network`) before the credential probe in
`cmd_auth_smoke`.

### BLOCKER 2 — the two paid Meshy commands submit with two of three barriers and no at-most-once claim

**Where:** `tools/assetgen/cli.py::cmd_shield_multiview`, `cmd_shield_3d`

**Reproduction (measured):** with a synthetic `MESHY_API_KEY`,
`EOM_ALLOW_PAID_PROVIDER_CALLS=1`, no `--confirm-plan`:

```
shield-multiview --submit  -> OUTBOUND: POST https://api.meshy.ai/openapi/v1/image-to-image
shield-3d --submit         -> OUTBOUND: POST https://api.meshy.ai/openapi/v1/multi-image-to-3d
shield-multiview --confirm-plan <64 hex>  -> SystemExit 2 (unrecognised argument)
```

Both create **paid** Meshy tasks. `--confirm-plan` is registered only on the
`autorig` subparser, so these commands cannot be given a confirmation even by an
operator who wants to.

**Broken contract:** "Ett verkligt provideranrop ska kräva samtliga följande"
— three barriers, for any real provider call. Also the at-most-once property:
because `authorize_paid_submission` is skipped, `claim_submission` never runs,
so nothing stops one approval from being spent twice on these paths. The only
remaining protection is the idempotency key, which stops an identical *request*
but not a second submission with any differing parameter.

**Actual risk:** real spend on Meshy with one fewer barrier than documented, and
no ledger entry to detect a replay. `shield-3d` additionally sits behind
`--confirm-visual-review`, which is a human-attestation flag, not a plan binding.

**Why the tests miss it:** the CLI barrier tests all target `autorig`. There is
no test that enumerates paid commands and asserts each one reaches the
chokepoint.

**Minimum fix:** add `--confirm-plan` to both subparsers and route both through
`authorize_paid_submission` with a plan built for the Meshy operation; or, if
those commands are considered dormant, make them refuse unconditionally until
they are wired to the chokepoint.

### HIGH 3 — a provider-chosen filename can write outside the artifact tree

**Where:** `tools/assetgen/orchestrator.py::download` (`destination =
outputs_dir / filename`), filename from
`providers/uthana.py::fetch` (`f"{provider_task_id}_rigged.glb"`)

**Reproduction (measured):** an offline double returning
`character.id = "../../../../ESCAPED"` caused the artifact to be written outside
the job outputs directory. With `character.id = "C:/Windows/Temp/EOM_AUDIT_ABS"`
the file was written to `C:\Windows\Temp\EOM_AUDIT_ABS_rigged.glb` — verified
present, then deleted by this audit. `pathlib` discards the left operand when the
right is absolute, so an absolute id becomes an absolute destination.

**Broken contract:** artifacts are supposed to land under
`artifacts/assetgen/jobs/<job_id>/outputs/`, and the plan's
`output_destination` names that location.

**Actual risk:** arbitrary file write at the privilege of the running user,
controlled by a provider response field. Reaching it requires a malicious or
compromised provider response (TLS makes a passive MITM impractical), so this is
not a present danger — but the first live call is also the first time an
unvalidated provider string is used to build a path, and the identifier is
echoed straight into a filename. Meshy is unaffected: all its
`suggested_filename` values are literals.

**Why the tests miss it:** the double always returns a well-behaved id, and no
test asserts that written paths stay inside the outputs directory.

**Minimum fix:** sanitise to a basename and re-anchor —
`destination = outputs_dir / Path(filename).name`, then assert
`destination.resolve().is_relative_to(outputs_dir.resolve())` and refuse
otherwise with a classified error.

### HIGH 4 — barrier 3 and the ledger claim are not at the network boundary

**Where:** `tools/assetgen/orchestrator.py::submit` vs
`cli.py::authorize_paid_submission`

**Reproduction (measured):**

```
JobOrchestrator(store, factory, live=True, opt_in=True).submit(request)
-> outbound request built with NO plan digest set | transport_calls=1
```

`submit()` calls only `_require_live` (barriers 1–2). `self.plan_digest` is used
solely to *record* which approval a task belongs to, and is empty on this path,
which also silently skips every `update_submission` call.

**Broken contract:** the comment on `_require_live` says a caller that
constructs an orchestrator directly "gets the same refusal". It gets two of the
three barriers, and none of the at-most-once protection.

**Actual risk:** any future caller, script or agent that builds an orchestrator
rather than shelling out to the CLI silently loses barrier 3 and the ledger.
Combined with HIGH 5 this is the most plausible route to a double charge.

**Why the tests miss it:** `orchestrator_for(...)` in the test suite always
passes `live=True, opt_in=True` and never asserts that a plan confirmation was
required, because at this layer none is.

**Minimum fix:** move the claim and the digest check into
`JobOrchestrator.submit` — require a non-empty `plan_digest` plus a successful
`claim_submission` before the create, and have the CLI supply the confirmed plan
rather than perform the enforcement.

### HIGH 5 — a rerun after an ambiguous create issues a second paid create

**Where:** `tools/assetgen/orchestrator.py::submit`

**Reproduction (measured):** a create that fails with a transport timeout is
recorded `status=FAILED, submission_outcome=UNKNOWN` with `create_calls=1`.
Running the identical request again against the same store:

```
create_calls went 1 -> 2
```

**Broken contract:** "Om det är oklart om en submission accepterades ska
körningen stanna med ett klassificerat osäkert tillstånd, inte försöka igen."
The state is recorded correctly and no *automatic* retry happens, but nothing
consults it on the next attempt.

**Why it happens:** an ambiguous create leaves no `provider_task_id`, so
`find_resumable` returns `None` and `submit` proceeds as if nothing had been
attempted. `submission_outcome == "UNKNOWN"` is written and then never read by
any decision.

**Actual risk:** exactly the double charge the design targets. Via `autorig` the
CLI ledger claim blocks it (the second run fails
`PROVIDER_SUBMISSION_ALREADY_RECORDED`), so the operator-facing path is safe
today. Via the shield commands or a direct orchestrator — neither of which
claims — the second create goes out and can pay twice.

**Why the tests miss it:** `test_a_create_timeout_does_not_resubmit` asserts
`create_calls == 1` within a **single** `submit()` call. No test performs a
second `submit()` after an ambiguous first one at the orchestrator layer.

**Minimum fix:** in `submit`, refuse when a manifest for this idempotency key
exists with `submission_outcome == "UNKNOWN"`, raising
`PROVIDER_SUBMISSION_OUTCOME_UNKNOWN` — a code that already exists and is
currently unused.

### HIGH 6 — the approved plan does not bind the host the request goes to

**Where:** `tools/assetgen/provider_plan.py::DIGESTED_KEYS`;
`providers/uthana.py::__post_init__` reading `UTHANA_API_BASE`
(and `MESHY_API_BASE` in the Meshy adapter)

**Reproduction (measured):**

```
UTHANA_API_BASE unset           -> plan digest D
UTHANA_API_BASE=https://attacker.example.invalid -> plan digest D  (unchanged)
adapter.base_url                -> https://attacker.example.invalid
```

The endpoint appears in the plan only inside `request_description`, which is
outside the digest. `digest_covers` therefore honestly lists what is bound — the
host simply is not in it.

**Broken contract:** "Alla beteendepåverkande fält ska omfattas av digesten."
The destination of an authenticated upload is as behaviour-affecting as a field
gets.

**Actual risk:** an environment variable — the one thing the design says must
never single-handedly influence provider traffic — redirects the upload and the
`Authorization` header to an arbitrary host without invalidating the approval.
The test suite clears these variables, so a stale export is invisible in tests
and effective in production. This is a genuine credential-exfiltration path
under a misconfigured or hostile environment.

**Why the tests miss it:** `conftest.py` deletes `UTHANA_API_BASE` and
`MESHY_API_BASE` before every test, so no test can observe their effect, and no
test asserts the resolved base URL is part of the digest.

**Minimum fix:** put the resolved base URL in the digested part of the plan and
have the adapter assert at submit time that its `base_url` equals the approved
one.

### HIGH 7 — the base64 Basic-auth token is not scrubbed

**Where:** `tools/assetgen/secret_guard.py::scrub` / `KEY_PATTERNS`;
`transport.py::HttpRequest` (a dataclass, so its generated `__repr__` prints
`headers`)

**Reproduction (measured), synthetic key throughout:**

| Surface | Plaintext key | Base64 of key |
| --- | --- | --- |
| `_headers()` dict, raw | no | **yes** |
| `_headers()` dict through `scrub_obj` | no | **yes** |
| `repr(HttpRequest)` | no | **yes** |
| `scrub_obj(repr(HttpRequest))` | no | **yes** |
| `HttpRequest.describe()` | no | no |
| provider error body echoing the key | no | no |

Uthana auth is `Basic base64("<key>:")`. `scrub` removes only exact registered
substrings — the raw key — so the base64 form survives, and the `basic_header`
regex needs the literal word `authorization` adjacent to `basic`, which does not
occur when a header dict is serialised as a JSON key/value pair.

**Broken contract:** "Inga nycklar i repo, rapporter, planfiler, command
history, exceptions eller loggar", and `HttpRequest.describe()`'s promise that
"headers are never included — they carry auth".

**Actual risk:** latent, not active. No current code path writes headers to a
report: `describe()` excludes them, and response snapshots contain no request
headers (verified by
`test_no_authorization_header_is_ever_written_to_a_response_snapshot`). But
`repr()` of a request is one `logging.debug(request)`, one
`pytest --showlocals`, or one unhandled traceback away, and base64 is not
obfuscation.

**Why the tests miss it:** the leak tests search for the **plaintext** key only,
and the snapshot test greps for the literal string `authorization`, which a
serialised value like `"Basic dGVzdDo="` does not contain.

**Minimum fix:** register the encoded form alongside the raw value in
`Credential.__post_init__`, add a pattern for a bare `Basic`/`Bearer` token, and
give `HttpRequest` a `__repr__` that omits `headers`.

### HIGH 8 — no test would notice the multipart contract being wrong

**Where:** `tools/assetgen/tests/provider_double.py::UthanaDouble.send`

**Reproduction (measured):** an in-memory sabotage renaming the GraphQL
multipart fields `operations` -> `ops` and `map` -> `m` — the exact shape the
provider requires:

```
EOM_SABOTAGE=multipart_field_names  ->  164 passed
```

**Broken contract:** the double's own docstring says mocking `submit()` "would
not exercise the multipart encoding", implying this one does. It *executes* the
encoder but never *validates* it: routing is a substring test
(`b"create_character" in body`), so any body containing that mutation name is
accepted regardless of its multipart framing.

**Actual risk:** the highest-value thing the offline double could have verified
about the first paid call is unverified. The multipart field names come from
documentation and remain untested; a wrong name fails at the provider, and for a
create the failure is `submission_outcome=UNKNOWN` — the ambiguous state that
requires manual reconciliation.

**Minimum fix:** have the double parse the multipart body — assert the boundary,
the `operations`/`map`/`0` part names, that `map` references
`variables.file`, and that the file part's bytes match the input — and refuse
anything else with a classified error.

### MEDIUM 9 — short credentials are never masked, and the test that claims otherwise uses a long value

**Where:** `secret_guard.py::register_secret` (`if value and len(value) >= 8`);
`test_provider_live_barriers.py::test_a_short_or_malformed_test_key_is_still_masked`

**Reproduction (measured):** with the key set to `ab12`,
`scrub("failed with ab12 in text")` returns the string unchanged. The test that
covers this registers `"shortkey123"` — 11 characters, above the floor — so it
passes without exercising the limitation its name describes.

**Broken contract:** "Maskera även korta eller felaktiga testnycklar."

**Actual risk:** low in absolute terms — a key under 8 characters is not a real
provider key — but the failure mode is a truncated or mistyped key appearing
verbatim in output while the suite asserts masking works.

**Minimum fix:** lower or remove the floor (a length-1 registered value costs one
`str.replace`), and change the test's value to something genuinely short.

### MEDIUM 10 — a corrupt or empty download is accepted as the artifact of a successful job

**Where:** `providers/uthana.py::download`, `orchestrator.py::download`

**Reproduction (measured):** with the bundle body replaced:

| Body served | Resulting status |
| --- | --- |
| `<html>error</html>` (18 bytes) | `DOWNLOADED` |
| empty (0 bytes) | `DOWNLOADED` |
| `gl` (truncated header) | `DOWNLOADED` |

The adapter writes `response.body` unconditionally; the orchestrator hashes the
file afterwards and records the hash without comparing it to anything. Uthana's
character-asset list *does* carry a `sha256` and `size` per asset — the adapter
reads them into `_character_summary` and never uses them to verify.

**Broken contract:** the §9 requirement "korrupt download når aldrig
ingestion/publish". What holds is weaker: a corrupt file is stored, correctly
hashed, and refused later by Godot's import.

**Actual risk:** moderate. The refusal does happen, one stage later, and nothing
publishes without an ACCEPTED chain. But a 0-byte artifact is recorded as the
verified output of a paid job, and in this suite the refusing stage (Godot) is a
stub, so "never reaches ingestion" is unproven here rather than proven.

**Why the tests miss it:** `test_a_corrupt_download_is_stored_but_its_hash_records_what_arrived`
is named for and asserts the current behaviour, including
`hash_matches is True`. It documents the gap rather than closing it.

**Minimum fix:** compare the downloaded bytes against the provider-declared
`sha256`/`size` when present, and refuse a zero-length body outright with a
classified `MISSING_OUTPUT`.

### MEDIUM 11 — the ledger is durable against process death, not against power loss

**Where:** `store.py::claim_submission`, `store.py::update_submission`

**Measured:** neither function calls `os.fsync`; there is no directory sync.
`claim_submission` uses `os.open(..., O_CREAT | O_EXCL | O_WRONLY)` + `os.write`;
`update_submission` uses `write_text` + `os.replace`.

**Broken contract:** the docstring says the claim "exists on disk BEFORE the
request goes out". After `os.write` the data is in the OS page cache: it survives
`kill -9` and an unhandled exception, but not a power loss or OS crash. §6 asks
for "flush/fsync av claim och job-id där kontraktet kräver kraschbeständighet".

**Actual risk:** low and narrow — a power loss inside the sub-second window
between the claim and the create could leave a paid task with no local record,
which is the double-charge scenario the claim exists to prevent. The exclusive
create and the atomic replace are correct; only durability is short of the claim.

**Minimum fix:** `os.fsync(handle)` before `os.close` in `claim_submission`, and
fsync the temp file before `os.replace` in `update_submission`. State plainly
that directory durability is not guaranteed on all filesystems.

### MEDIUM 12 — the credential-ordering guarantee only covers reads that go through the seam

**Where:** `test_provider_live_barriers.py::test_building_an_adapter_reads_no_credential`

**Reproduction (measured):** two sabotages that both restore the old eager read:

| Sabotage | Suite result |
| --- | --- |
| eager read via `uthana.load_credential` (the patched symbol) | **1 failed** |
| eager read via `os.environ.get("UTHANA_API_KEY")` | **164 passed** |

**Broken contract:** none literally — the test does what it says. But the
property being claimed is "constructing an adapter reads no credential", and the
oracle is a monkeypatched function name, so it can only see reads that go through
that name.

**Actual risk:** a future adapter that reads the environment directly would
reintroduce the exact ordering bug this slice fixed, with a green suite.

**Minimum fix:** assert against a recording `os.environ` proxy (this audit's
probe C does this in about fifteen lines) rather than against a patched symbol.

### MEDIUM 13 — `provider-plan` reads the credential value while reporting that it did not

**Where:** `provider_plan.py::assert_no_credential_values` (line ~320),
called from `build_plan`; output field in `cli.py::cmd_provider_plan`

**Reproduction (measured), recording `os.environ` proxy:**

```
phase: build_plan (offline plan path)
credential_reads: [{var: UTHANA_API_KEY, site: provider_plan.py:320:assert_no_credential_values}]
```

while the command prints `"credential_read": false`.

**Broken contract:** "Credentials får endast hämtas i den slutliga livevägen,
efter att alla tre spärrarna ovan passerat."

**Actual risk:** very low as a leak — the read exists precisely to assert the
value is *absent* from the plan, and the value is discarded. The problem is
honesty: a machine-readable field asserts something false, and the ordering
invariant has an exception that the documentation does not mention. Note the
refused-run path is clean: a run refused at a barrier performed **zero**
credential reads, measured.

**Minimum fix:** either drop the environment comparison and rely on the pattern
check plus the fact that no code path writes a value, or keep it and change the
field to `credential_value_read_for_leak_check: true` with a documented
rationale.

### MEDIUM 14 — the plan's declared limits are descriptive, not enforced

**Where:** `provider_plan.py` limits/timeouts vs `orchestrator.poll`,
`providers/uthana.py::download`, `cli.py` argument defaults

**Measured:**

| Plan declares | What actually runs |
| --- | --- |
| `max_poll_attempts: 60` | 60 **orchestrator** attempts, each of which retries up to 5 times inside `send_with_retry` — measured 15 provider requests for `max_attempts=3`, so up to ~300 for 60 |
| `max_download_attempts: 3` | `UthanaProvider.download` calls `transport.send` exactly once; no retry exists |
| `timeouts.poll_total_s: 1800` | `poll --timeout` CLI default, freely overridable, not read from the plan |
| `output_destination` | for autorig this is the literal template `artifacts/assetgen/jobs/<job_id>/outputs/<character-id>_rigged.glb`; the real path is derived at runtime from `job_id` |

Every one of these fields *is* inside the digest — mutating any of them changes
it, verified — so the approval binds the **document**. It does not bind the
**run**, because no runtime value is read back from the plan.

**Actual risk:** no spend risk (polls and downloads create nothing) but two real
consequences: the declared poll budget understates provider request volume by 5x,
which is a rate-limit and reputation concern on a first live call; and the
documented promise "what was approved is what runs" is not mechanically true.
The `send_with_retry` backoff also sleeps with the real clock, not the
orchestrator's injected `sleep`, which is why one audit probe took 41 seconds.

**Minimum fix:** pass the plan's limits and timeouts into `poll`/`download`
instead of using defaults, and either implement download retries or set
`max_download_attempts` to 1.

### MEDIUM 15 — proxy variables are not cleared, and loopback is a permitted egress channel

**Where:** `tests/conftest.py::PROVIDER_ENV_VARS`;
`net_guard.py::LOOPBACK_HOSTS`

**Measured:** `conftest.py` clears `MESHY_API_KEY`, `MESHY_API_BASE`,
`UTHANA_API_KEY`, `UTHANA_API_BASE` and the opt-in. It does **not** clear
`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` or their lowercase forms.
The tripwire allows `127.0.0.1`, `::1` and `localhost` by design, so a proxy
listening on loopback is an allowed path out of the process.

In one direct attempt, urllib with `HTTP_PROXY=http://127.0.0.1:9` *was* caught —
but by a hostname resolution it performed first, not by the proxy connection
itself. That is incidental: `_is_loopback(("127.0.0.1", 9))` returns `True`, so
the connection is permitted by policy.

**Actual risk:** low on a developer machine with no proxy, and the loopback
allowance is a deliberate, reasonable trade. But the combination means "the
suite cannot reach a provider" is a statement about the *absence of a local
proxy*, not a guarantee the tripwire enforces.

**Minimum fix:** add the proxy variables to `PROVIDER_ENV_VARS`, and document
that loopback is intentionally permitted.

### LOW 16 — tripwire coverage gaps

Measured against unreachable addresses, so "not blocked" means the guard passed
the call to the OS:

| Vector | Caught |
| --- | --- |
| `socket.connect` IPv4 / IPv6 | yes |
| `socket.connect_ex` | yes |
| `socket.create_connection` | yes |
| `socket.getaddrinfo` | yes |

The guard restores all four patched attributes on exit (verified) and is armed
`autouse` for every test (verified).

**What the tripwire proves:** no in-process, connection-oriented egress via the
standard socket API during the suite. **What it does not prove:** that a spawned
process has no network. `rig_ingest` spawns Godot, so any claim of end-to-end
offline behaviour covering ingestion rests on Godot's own behaviour, not on this
hook. `gethostbyname` and UDP are minor because nothing in the codebase uses
them.

### LOW 17 — `require_credential` defaults to `True` in both adapters

`UthanaProvider(transport=...)` reads the key at construction unless
`require_credential=False` is passed. The CLI and `build_autorig_plan` pass
`False`; the default is the unsafe direction. Inverting it would make lazy
loading the default rather than an opt-in.

### LOW 18 — one unreadable manifest disables the idempotency lookup for every job

`JobStore.find_by_idempotency_key` iterates `list_jobs()`, which reads every
manifest. `MANIFEST_SCHEMA_VERSION` was bumped to 2 in this slice, so a v1
manifest left on disk raises during that scan and every `submit` fails. The
direction is fail-closed and therefore safe, but the diagnosis an operator sees
will be a schema error on an unrelated job.

### LOW 19 — `PROVIDER_PLAN_NOT_EXECUTABLE` is unreachable through the CLI

`cmd_autorig` runs `evaluate_candidates` and returns `PRE_UPLOAD_GATE_FAILED`
before it builds a plan. Since `build_autorig_plan` derives `executable` from the
same gate, a plan that reaches barrier 3 is always executable. The refusal class
is correct and tested, but only synthetically; no CLI input can produce it.

### LOW 20 — the input file is read twice between hashing and upload

Measured: `build_plan` hashes the file with a streaming read; `_build_multipart`
later calls `read_bytes` on it again. A write landing between the two uploads
bytes that were never approved. The window is small and requires local write
access, and the digest still binds the hash that *was* observed. Reading once
into memory (or re-verifying the hash immediately before the send) would close
it.

### LOW 21 — the previous slice report undercounted its own sabotage result

That report stated that disabling the opt-in barrier and re-enabling create
retries "turned 10 tests red". Measured here: 9 red for the opt-in sabotage
alone, 2 for the retry sabotage alone, and **11** for both together. The claim
was directionally right and numerically wrong.

## 4. What holds up

These were attacked and did not break. They are the load-bearing parts of the
slice.

**The barrier logic itself is exactly right.** All nineteen permutations behave
as documented — every single barrier and every pair refuses with the correct
distinct code, only all three together pass, and the refusal reported is always
the *first* missing barrier, so a refusal never depends on whether a key is set.
Only the exact opt-in value counts: `true`, `yes`, `2`, `0` and `01` are all
refused. A digest differing in case or surrounded by whitespace is accepted,
which is deliberate normalisation of hex — not a weakness.

**A refused run reads no credential.** Measured with a recording `os.environ`:
zero reads on the refused path. Adapter construction reads nothing. This is the
single most important ordering property of the slice and it holds.

**Plan digest coverage is genuinely complete for everything in the plan.** All
fifteen mutations changed the digest: provider, operation, each operation
parameter (including `include_fingers`), input content at identical size, input
size, output destination, the paid flag, credential variable names, all three
timeouts, both attempt limits, declared cost, and the preflight verdict.
Description-only fields do not change it, so regenerating an unchanged plan
reproduces the approval. `digest_covers` is recorded inside the plan, so what is
bound is auditable rather than implied.

**The stored digest is never trusted.** Editing `plan_sha256` in a plan file does
not make it confirmable — the digest is recomputed from content and the edited
plan is refused `PROVIDER_PLAN_DIGEST_MISMATCH`.

**Plan TOCTOU binding is sound.** `cmd_autorig` rebuilds the plan from the
current file and compares the operator's digest against *that*, so swapping the
asset after approval is refused `PROVIDER_PLAN_DIGEST_MISMATCH`. A correctly
hashed old plan cannot approve a different current asset — the specific property
§5 demanded. Symlinks are resolved before hashing, so retargeting one changes the
digest.

**Creates are never retried, and ambiguity is classified.** Measured for both a
transport timeout and HTTP 503: `create_calls == 1` and
`submission_outcome == "UNKNOWN"`, not `FAILED`.

**The claim primitive is correct.** A second claim of the same digest raises
`FileExistsError`; a *corrupt* ledger record still blocks a new claim, which is
the right direction; a crash after the claim but before the request leaves the
claim in place, so a replay is blocked rather than invited.

**Resume works and does not re-pay.** A successful create followed by an
identical rerun resumes with `create_calls` unchanged, and a brand-new store
object loaded from disk finds the same `provider_task_id`.

**Poll, download and cancel all require barriers 1 and 2.** Verified at the
transport counter, including `download` on a job that already has recorded URLs
(so the barrier is what refuses, not a missing precondition). The poll attempt
cap is honoured even with an effectively infinite deadline.

**Publishing is atomic and gated on acceptance.** `publish_atomically` writes
beside the destination and uses `os.replace`, so a reader sees the old artifact
or the new one. A compiler FAIL and a grip FAIL both leave the published path
absent. Note the Godot verdict is fabricated in these tests: what is proven is
the *wiring* — that `rig_ingest` publishes only on an accepted, certified chain.
The certification logic itself is `slice a2`'s evidence, not this suite's.

**The double is structurally independent where it matters.** It shares only
`HttpRequest`/`HttpResponse` and the error taxonomy with production code. It does
not import the adapter's GraphQL query strings, its response parsing, or its
multipart encoder, so the adapter's parsing is genuinely exercised rather than
mirrored — the GraphQL-200-with-`errors` quirk, the "no bundle asset yet means
still rigging" rule and the authenticated bundle download all run through
production code. The gap is the multipart *request* shape (HIGH 8), not the
response handling.

**The suite is isolated from the host machine.** Credentials and the opt-in are
cleared per test, the tripwire is armed `autouse`, and call counters rather than
reported statuses are what the assertions read.
